## State-transition assessment

The new request path normalizes input, routes the reserved shape before ordinary provider readiness, applies existing network/phone quotas and CAPTCHA requirements, and calls `test_signin_direct_begin`. That function takes the switch lock then phone lock, rechecks both switches and active/unexpired allowlist membership, excludes staff/clinic identities, and reuses the existing challenge store without a provider request. Its synthetic seal is not an OTP. A random browser nonce is stored in an HttpOnly, SameSite=Strict cookie, with Secure in production; only its SHA-256 digest reaches SQL.

Verification consumes the browser-bound challenge through `test_signin_direct_check` before any Auth mutation. The inherited admission predicate is repeated; five failed guesses in a fifteen-minute window apply across challenges; challenge expiry remains two minutes. A checked challenge blocks another active exchange for the same phone. The code uses bcrypt and the replacement comparison performs a fixed 32-byte digest comparison. The challenge replay guard is atomic under the same lock order. This is source analysis plus mocked module testing, not a measured database timing or concurrency proof. The fixed loop removes early-exit text equality from the stored-hash comparison; it is not a formal constant-time guarantee for PostgreSQL execution or the complete endpoint, whose rejection branches intentionally do different work.

The separate exchange client receives a fresh 32-byte random password, creates or updates the fictional Auth identity and obtains a normal password-grant session. The privileged RPC client is separate, so signing in cannot replace its service credentials. Returned phone, user ID, JWT subject and authenticated role are checked. Final SQL admission verifies the session row belongs to the user, the Auth role is authenticated, and the challenge/phone/nonce/digest and allowlist still agree. Cookies are installed only afterward. Failure tries local sign-out and challenge abandonment; no password or session is returned by the server action. The password is not passed to application logging. F1 concerns the earlier irreversible credential mutation across these separate transactions.

All four new wrappers enforce `auth.role() = service_role`, revoke PUBLIC/anon/authenticated grants and grant only service_role. The internal hash helper is not callable by those roles. SECURITY DEFINER functions set an empty search_path and qualify non-built-in tables/functions; unqualified functions such as `get_byte` and `pg_advisory_xact_lock` are pg_catalog built-ins. Switch → phone → row lock ordering matches the guarded #700 operations. Membership writers do not participate in this exchange lock, which matters for F1. The SQL tests use sequential interleavings; they are not two-connection deadlock/race tests.

Audit coverage is narrower than “every outcome” literally: the named SQL admission, code acceptance and ordinary refusal paths write existing `test_signin.*` events, with last four digits and fixed outcomes. No new vocabulary was introduced. Malformed action inputs, request CAPTCHA failures and network quota refusals return before those SQL events, and a service-only finalization with an otherwise matching request/session but a wrong nonce/digest can reach inherited `auth_code_request_verified` and return false without a `test_signin.refused` event. The web path's preceding check prevents that ordinary mismatch case. Thus the tests establish selected audited outcomes, not every possible service-RPC argument or pre-admission HTTP refusal. Treat broader audit wording as unproved; this is not a new browser authorization bypass.

No new seed rows enable the database switch or populate the allowlist. The new migration sorts after main's latest migration and does not modify an applied migration. The environment flag is exact-string `true`; unset/false/TRUE fail admission. `scripts/seed-environment.sql` and its expected values are unchanged. No live production-state check was performed.
