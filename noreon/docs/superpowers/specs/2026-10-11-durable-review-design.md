# Durable review loop

Status: proposed for Claude review under the user's continuous-execution delegation. Publication integrity is committed as 0c6b07e; continuity as 9c4e23f. This is stage three of five, not a replacement for doctor efficiency or ongoing follow-up.

## Outcome and current defect

A member's approved plan stays available when new evidence arrives. One persistent task tells the assigned doctor that evidence needs review; repeated changes update that task rather than creating duplicate work. The member sees both the current plan and pending review. Closing a task must prove which evidence was reviewed. Urgent findings keep their existing precedence and never become a routine no-change review.

Currently `lib/staff/queue.ts` returns published before checking changed evidence. `serviceNextAction` similarly returns null whenever a publication exists. Evidence already has an authoritative case counter and parent-row lock, but there is no durable review outcome or published evidence watermark. Queue list reads also omit evidence counters. Deriving a badge from draft freshness alone would lose the distinction between editing a draft and completing clinical review.

## Persistence and concurrency

Use a dedicated `workspace_review_tasks` table, with RLS enabled and direct browser access denied. Columns: id, case_id (cascade with disposable case), status (open/completed), opened_evidence_revision, target_evidence_revision, owner_id, opened_at, updated_at, completed_at, completed_by, completed_evidence_revision, outcome (published/no-change), and completion_note. A partial unique index permits at most one open task per case. Retain completed tasks; subsequent evidence creates a new task. Case assignment remains authoritative: synchronize open-task ownership with it, preserve completed owner attribution, and show unassigned/inactive coverage in backoffice rather than hiding the task.

An AFTER case INSERT/UPDATE trigger reconciles a task under the existing case-row lock when evidence_revision advances. It creates a task when a completed assessment or existing publication makes clinical review meaningful. Evidence arriving before questionnaire completion remains stored; completing the questionnaire opens the task for the current revision. An already-open task advances target_evidence_revision without changing its identity or original opened_at, including while a questionnaire is being revised. Report changes already advance the case counter under that lock. Care acknowledgements, medication check-ins, presentation-only changes and draft edits must not create tasks.

Publication stamps its exact evidence revision into the publication and completes the current task atomically after all existing publication checks and report snapshots succeed. Any failure rolls back both. A concurrent evidence write either precedes publication (stale publication rejected) or follows it (new open task); it cannot be swallowed by completion. Generic case saves cannot forge publication watermarks or task fields; table mutation is available only to internal trigger/command functions.

Legacy cases lack a trustworthy published evidence watermark. Do not infer one from a recently saved draft or timestamp. Backfill one open verification task for eligible existing cases with an explicit legacy reason; keep their published care intact. New publications/completed reviews supply trustworthy watermarks going forward.

## Explicit no-change outcome

Provide a doctor-only `workspace_complete_review_no_change` command with expected case revision, task ID, target evidence revision and a required bounded note. Under the case lock it rechecks current assigned active doctor/clinic, the open task and exact evidence revision. Require a current publication, complete nonurgent questionnaire, applicable results and consultation, current report approvals, and a draft saved against current evidence. Require that saved treatment draft equals the existing published draft; changed treatment must use publication. No-change completion records the reviewed evidence and attribution, advances case revision, and leaves publication, published report snapshots, medication orders and acknowledgements unchanged. This cannot expose newly imported unpublished results: those require publication. The UI explains that consequence instead of implying new results were released.

Both completion routes preserve an audit outcome. Failed/stale completion leaves the task open, preserves typed notes and offers refresh. No manual checkbox may simply erase the pending task.

## Read model and interface

Include current task and recent completed tasks in the same coherent case snapshot as evidence, workflow and reports. Queue queries join/read the task and evidence counters explicitly; do not reconstruct task state from a stale JSON workflow. Doctor queue prioritizes an open reassessment even when a plan exists, while indicating blockers (unfinished questionnaire, missing results, consultation) instead of pretending it is ready to publish. Backoffice lists unassigned/inactive-owner tasks. No new escalation deadline or clinical urgency rule is invented; existing result-based review windows remain identified as such, with task opened time shown separately.

The doctor case view shows what evidence changed, task owner and status, and offers the explicit no-change outcome alongside publication after prerequisites are met. History shows completed outcome, doctor, note and exact evidence revision. Member care/service views show pending review alongside the existing approved plan and ongoing medication controls. Existing urgent presentation remains first. Initial review continues to show existing booking/questionnaire prerequisites.

Shared mode is the authoritative multi-user implementation. The fictional browser-only mode serializes server-visible task transitions in its bounded cookie session, with its existing explicit storage-limit behavior. It supports publication completion only; reports remain in browser memory and have a separate status. It does not imply cross-user assignment or SQL durability. Existing verified-account care RPCs remain separate, as in stages one and two.

## Design review resolutions

Claude identified six gaps. The user resolved G1: BP readings advance open tasks but do not reopen closed tasks. As a separate engineering classification, name-only identity changes also advance existing tasks only; date of birth and biological sex remain clinical context changes that open review. Questionnaire, report, requirement and receipt changes open eligible tasks. No value threshold or escalation policy is inferred.

G2: superseding the earlier permissive no-change paragraph, no-change MUST reject when current approved reports or active receipts differ from what the existing publication covers. Compare current report IDs, record revisions and approval payloads to their published snapshots tied to the current publication key; reject added, changed, deleted or unpublished reports. Persist a publication report-coverage manifest for reliable deletion detection. Compare current active requirement-specific receipts to publication.resultReceipts exactly. A legacy publication without a trustworthy manifest cannot use no-change; it must republish. This releases reviewed results through the established publication boundary and preserves unchanged medication identity. No-change remains available only when no new result publication is needed.

G3: do not infer change kinds from an evidence-log row before it exists. Implement internal workspace_reconcile_review_task(case_id, kinds). Case-state AFTER trigger derives changed projection keys directly from OLD and NEW state. It ignores counter-only updates. Report trigger invokes reconciliation explicitly after incrementing the case counter and inserting its evidence log; all under the existing parent lock. Assignment synchronization is a separate case-column transition. Functions lock case before task consistently. Initial eligibility transition and legacy backfill are explicit reasons, not fabricated evidence changes.

G4: listCases uses one embedded task select with evidence_revision and reviewed_evidence_revision; pass the task explicitly through queueItem/operationsItem, not workflow JSON. Service role receives SELECT only on the task table; task writes occur through security-definer functions with PUBLIC/anon/authenticated execution revoked. Existing authenticated staff checks and doctor assigned-case query filter remain. Admin coverage views retain inactive/unassigned cases. Coherent detail snapshots include task data in the existing snapshot function.

G5: backfill exactly nonexpired cases having a completed assessment or existing publication, with reason legacy-verification; unique-open-task conflict is ignored for idempotence. Admin reset keeps an open task targeting initial review and retains completed task history. Explicit reset reconciliation handles an evidence-equivalent reset too, so no open task incorrectly disappears when publication is cleared.

G6: no-change compares saved and published drafts as jsonb; checks draft_evidence_revision = case.evidence_revision = task.target_evidence_revision under lock. Store reviewed_evidence_revision as a case column, updated only by completion commands. Ordinary save RPC does not accept it. Record review.no_change/review.published through the existing attributed activity mechanism; extend the permitted event kinds explicitly. Publication coverage fields live inside its already-protected publication object. Completion preserves outcome, note, actor and reviewed revision independently of later task creation or reset.
