# Plan-notice producer and worker

Implements the next stage of the messaging design. Routine implementation choices are delegated overnight. No environment flags or provider credentials are set, and no live messages are authorized by this work.

A service-only candidate RPC discovers active real plans after publication (including scheduled future plans once due), with current consent and no existing logical job. The producer uses keyset pagination to advance past individual failing sources within each run. It scans at most 1,000 candidates, enqueues at most 100, and budgets five seconds for source processing; failures are counted and do not prevent inspecting the existing send queue. This is bounded progress, not a claim of fairness past 1,000 persistent failures or repeatedly slow database calls; persistent backoff remains part of activation hardening. The existing enqueue RPC remains authoritative under locks.

A worker scans queued jobs in stable order after excluding quiet-hour jobs before the limit, calls the authoritative begin RPC immediately before a single provider request, and persists submission and initial delivery facts. Quiet or stale jobs never block later jobs in that run. Limits: 1,000 source candidates / 100 enqueues, 25 submission candidates and 45 seconds per invocation; sequential submission is deliberately conservative until provider rate limits are known. Database calls have short abort deadlines. Provider calls already have a ten-second timeout. Check the remaining budget before starting a submission, reserving 30 seconds for begin, the provider request, outcome write, possible reread and delivery-event write.

Stop the submission phase on provider rejections/unknown outcomes or a submission storage failure, and report counts/error category without phone numbers or raw exceptions. Failed and unknown attempts remain durable for operations. An early callback may already resolve submission; false finish results require an authoritative reread and reference comparison. Never retry unknown submission. Existing provider-failure recovery/circuit breaker gates remain required before activation; this worker is not activated merely because its code exists.

Configuration for worker and callback comes from one server module. Real project credentials are explicit, no shared-demo fallback. Outbound activation requires NOREON_MESSAGE_DELIVERY_ENABLED=true and the callback enabled; demo deployments are always denied. The internal route authenticates the cron secret using a timing-safe comparison. A five-minute cron schedule is an activation step, not installed while the provider is unavailable. No job is enqueued while disabled. A separate NOREON_MESSAGE_RECOVERY_READY=true acknowledgement is required; leave it unset until persistent failure controls, daily cost limits, reconciliation and controlled rejected-attempt recovery are implemented and verified.

Tests cover source publication time, backlog progress, consent changes, replay deduplication, disabled/auth gates, one send, early callback resolution, budget exhaustion and safe stop on ambiguous/rejected/provider or storage failure. Run isolated migration replay, generated types, full checks and Claude's focused review before release.
