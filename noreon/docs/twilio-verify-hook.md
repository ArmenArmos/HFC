# Twilio Verify SMS hook

Implementation is disabled until explicitly configured. No live delivery is claimed by mocked tests.

Supabase generates and validates six-digit codes. Its signed Send SMS hook submits the custom code to the configured Twilio Verify service with SMS channel and English locale. Enable Custom Verification Code on that service before setting readiness. The adapter accepts a VE receipt only when account, service, recipient, channel and pending status all match.

Runtime requires the existing real-app, registration, Armenia-only and hook-ready gates, plus `NOREON_PHONE_OTP_PROVIDER=twilio-verify-hook`, `NOREON_TWILIO_VERIFY_READY=true`, and `NOREON_TWILIO_VERIFY_SERVICE_SID`. It uses the Twilio account with separate `NOREON_TWILIO_VERIFY_API_KEY_SID` and `NOREON_TWILIO_VERIFY_API_KEY_SECRET` credentials. Existing messaging credentials remain independent. The runtime needs Verification create/update permissions; provider inspection may also require service/verification read permissions.

Before any provider request, the database reserves `verify_attempt_ceiling_micros`, a separately approved conservative total covering the Verify custom-code fee for every attempt and all SMS segments/fees for the selected service/template/route. Configure it with `configure_auth_verify_spend(expected_revision, ceiling_micros, operator_label)`. Its migration default is zero. The existing spend policy must also be enabled, USD, current and Armenia-only. The shared daily ceiling is always at most $5. No tariff is guessed or enabled by the migration. Reservations are never refunded. One bounded request is allowed per hook claim; ambiguous sends retain the reservation and pause dispatch.

An HMAC of account, service, phone and OTP is stored with the immutable send claim. No raw phone or OTP is persisted in this ledger. Web confirmation calls Supabase `verifyOtp` first and requires its returned phone to match. Only then does the server claim feedback for an accepted matching send created within ten minutes. The database chooses the VE; the browser never supplies a VE. Feedback sends once and records accepted, failed or unknown. A crash leaves submitting, and no automatic retry repeats an uncertain approval. Authentication remains successful even if feedback is unavailable. Operators must reconcile submitting/unknown/failed feedback in `auth_verify_feedback` against Twilio before any manual action; never approve a VE based only on a phone number.

The updated native client routes SDK phone confirmation through the fixed `/api/native/verify-phone` app endpoint. The endpoint strictly accepts Armenia phone/six-digit code/SMS type, checks native/app/provider readiness, performs actual Supabase verification with the anon credential, binds the returned phone and uses the same feedback helper. It returns the Supabase session format so the existing SDK/SecureStore lifetime handles persistence. It strips incoming auth/IP headers, has bounded input/time, never falls back or retries, and keeps Supabase OTP rate limits (server proxy IP may throttle more strictly). CAPTCHA-protected send remains unchanged. Older native binaries that call Supabase directly must be retired before activating the global custom-code hook; source implementation does not prove a distributed binary has been updated. Native runtime also requires `NOREON_NATIVE_JOURNEY_ENABLED=true`.

## Reviewed findings

- P1 changed-code resend: a separately keyed account/service/recipient digest serializes sends. A new reservation becomes the active claim before canceling the prior exact VE. Pending/unknown send or feedback blocks another send; old feedback cannot claim after a resend wins. Only a matching canceled receipt or bounded HTTP 404 with Twilio error code 20404 authorizes the next create. Cancellation ambiguity holds the entire reservation and pauses dispatch. No raw recipient/code enters these tables.
- P2 native deadline: after actual Supabase success and identity matching, feedback is limited by the remaining request deadline; stalled/throwing feedback cannot turn the consumed code and confirmed session into an error response. A client-aborted request does not start new feedback work.
- Service-role key resolution: the signed hook's store factory resolves the existing server `SUPABASE_SERVICE_ROLE_KEY` only when `NOREON_MESSAGING_SERVICE_ROLE_KEY` is undefined, after signature validation. Empty or invalid explicit overrides fail closed. Feedback uses the same resolution after successful OTP verification.

The custom-code fee is charged for every attempt, not only successful verification. The approved ceiling must cover that fee plus all SMS segments/fees. Provider pricing must be checked at activation; no tariff is embedded in code.

Final local verification after review fixes: full isolated replay through `20261013082006` succeeded; both Verify SQL suites and the existing Twilio SQL suite passed. Real concurrent PostgreSQL sessions proved one sender/one reservation per recipient and feedback-versus-resend exclusion; the existing shared-cap/idempotency concurrency suite also passed. Types were regenerated from that replay. Fixtures were removed and checked: no attempts, recipient identities, feedback or spend totals; policy disabled, Verify ceiling zero, dispatch unpaused.
